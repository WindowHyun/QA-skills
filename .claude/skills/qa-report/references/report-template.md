# 리포트 구조

아래 구조를 그대로 따른다. 섹션은 하나도 빼지 않는다. 해당 사항이 없으면 "해당 없음"이라고 적는다 —
QA는 "섹션이 없는 것"과 "없다고 확인된 것"을 구분해야 한다.

작성 규약 네 가지:

- **절차**는 한 칸 안에 `1) ... 2) ...` 형태로 이어 쓴다(표가 깨지지 않게).
- **근거**에는 반드시 `파일:라인`을 남긴다.
- **공통 사전조건은 표 위로 뺀다.** 여러 TC가 같은 계정·데이터·환경을 쓰면 표 앞에 `SETUP` 블록을 두고,
  `사전조건` 칸에는 `SETUP + 추가 조건`만 적는다. 같은 셋업을 매 행에 반복하면 표를 읽을 수 없게 된다.
- **이미 깨져 있는 케이스는 기대값과 현재 동작을 함께 적는다.** QA는 "무엇이 맞는지"와 "지금 무엇이 나오는지"가
  둘 다 있어야 수정 여부를 판정할 수 있다. 형식: `기대: 총액 0원 이상 / 현재: total=-5000 — 실패 예상 (D-1)`.
  이 표기가 없으면 QA는 이미 알려진 결함을 버그로 다시 올리느라 시간을 쓴다.

```markdown
# QA 리포트: <대상 이름>

| 항목 | 내용 |
|---|---|
| 작성일 | YYYY-MM-DD |
| 분석 대상 | <PR #12 / feature/xxx 브랜치 / src/payment 모듈> |
| 비교 기준 | <origin/main @ abc1234> |
| 변경 규모 | 파일 N개, +N/-N 라인 |
| 분석 제외 | <제외한 범위와 이유. 없으면 "없음"> |

## 1. 요약

<이 변경이 무엇을 하는지, QA 관점에서 가장 조심해야 할 것이 무엇인지 3~5문장.>

| 우선순위 | 위험 지점 | 테스트 케이스 |
|---|---|---|
| P0 | N건 | N건 |
| P1 | N건 | N건 |
| P2 | N건 | N건 |

두 열의 숫자는 서로 달라도 된다. 위험 하나가 여러 TC로 갈라지고, 회귀 확인 TC는 대응하는 위험이 없다.
각 열의 합계가 본문(4장·6장)의 항목 수와 맞기만 하면 된다.

**릴리즈 전 필수 확인**: TC-01, TC-04 <P0 케이스 ID 나열>

## 2. 변경 내용 (기능 관점)

### 2.1 의도된 기능 변경
- <사용자/시스템 관점에서 무엇이 달라졌는가. 코드 나열이 아니라 동작 서술.> (`파일:라인`)

### 2.2 조용히 같이 바뀐 것
PR 제목·설명에 없는데 디프에 섞여 들어온 변경. **여기가 사고가 나는 자리다** —
리뷰어도 QA도 예상하지 못하고, 커밋 메시지에 근거가 없어 의도인지 실수인지 판단할 수 없다.
권한 검사 삭제, 처리 순서 변경, 에러 처리 제거, 기본값 변경을 특히 눈여겨본다. 없으면 "없음".

- <무엇이, 어디서, main 대비 어떻게 바뀌었는가> (`파일:라인`, main의 `파일:라인` 대비)

## 3. 회귀 영향 범위

변경된 공통 코드와 그 호출 지점. QA는 변경 기능뿐 아니라 여기 나열된 기존 기능도 확인해야 한다.

**(1) 변경된 코드를 쓰는 곳** — 이번 변경이 기존 기능을 깨뜨리는 방향

| 변경된 대상 | 호출/사용 지점 | 영향 받는 기능 |
|---|---|---|
| `calcDiscount()` (`src/order/price.ts:88`) | `src/order/checkout.ts:140`, `src/cart/summary.ts:52` | 결제 금액 계산, 장바구니 합계 |

**(2) 변경된 코드가 쓰는 곳** — 기존 코드가 새 사용 방식에 못 버티는 방향

변경 파일이 호출하는 **기존 함수를 빠짐없이 나열**하고, 각각 "이번 변경으로 호출 순서·빈도·동시성·입력 범위가
달라지는가"에 한 줄로 답한다. 디프에 없다는 이유로 빼지 않는다 —
원래부터 있던 경쟁 상태나 반복 질의는 **호출 방식이 바뀌는 순간 처음으로 터진다.**
달라지는 게 없으면 "변화 없음"이라고 적는다. 적어봐야 확인했다는 증거가 된다.

| 호출되는 기존 코드 | 이번 변경으로 달라지는 점 | 그래서 새로 생기는 위험 |
|---|---|---|
| `reserveStock()` (`src/inventory.ts:4`) | 호출 시점이 저장 이후로 이동 | 실패해도 주문이 남음 → R-3 |
| `getProduct()` (`src/db.ts:20`) | 항목 수만큼 반복 호출(변화 없음) | 장바구니가 커지면 N+1 → R-12 |

## 4. 위험 지점

- **근거**: `src/order/price.ts:88-96`
- **무슨 일이 일어나는가**: <코드 로직상 어떤 조건에서 어떻게 잘못되는지 구체적으로>
- **영향**: <사용자/데이터에 미치는 결과>
- **관련 테스트 케이스**: TC-01, TC-02

### R-2. ... (반복)

## 5. 발견된 결함

코드를 읽거나 실행해 **테스트 이전에 이미 확정된** 문제. 없으면 "없음".

4장(위험 지점)과 내용이 겹치는 것은 정상이다. 역할이 다르다 — 4장은 개발자가 읽는 **메커니즘과 영향** 서술,
5장은 관리자가 훑는 **한 줄 사실 + 위치 + 심각도** 목록이다. 5장에 메커니즘을 다시 풀어쓰지 말고 R 번호로 연결한다.

R과 D는 1:1이 아니어도 된다. 검증해야 하지만 아직 결함이라 단정할 수 없는 R(대응 D 없음),
코드만 보고 확정했지만 테스트 대상이 아닌 D(대응 R 없음) 모두 정상이다. 번호를 억지로 맞추지 않는다.

| ID | 내용 | 위치 | 심각도 |
|---|---|---|---|
| D-1 | 쿠폰 금액이 주문액보다 크면 결제 금액이 음수가 된다 | `src/order/price.ts:91` | P0 |

## 6. 테스트 케이스

> **공통 사전조건(SETUP) / 실행 방법**
>
> <모든 TC가 공유하는 계정·데이터·환경.>
>
> UI나 실제 엔드포인트로 도달할 수 없는 저장소라면 **복사해서 바로 돌릴 수 있는 하네스 코드를 여기에 통째로 넣는다.**
> 픽스처 준비, 목 `req`/`res` 객체, 실행 명령까지 포함한다. "직접 호출하세요"라고만 적으면
> QA가 그 하네스를 스스로 만들어야 하고, 대개 거기서 멈춘다.

| TC | P | 검증 항목 | 사전조건 | 절차 | 기대 결과 | 근거 | 자동화 |
|---|---|---|---|---|---|---|---|
| TC-01 | P0 | 쿠폰 금액 > 주문 금액 | 10,000원 쿠폰 보유, 장바구니 5,000원 | 1) 장바구니 진입 2) 쿠폰 적용 3) 결제 진행 | 결제 금액 0원, 음수 불가, 잔액 소멸 안내 노출 | `src/order/price.ts:91` | 없음 |
| TC-02 | P1 | 쿠폰 중복 적용 | 쿠폰 2장 보유 | 1) 쿠폰 A 적용 2) 쿠폰 B 추가 적용 시도 | 1장만 적용, 안내 메시지 노출 | `src/order/coupon.ts:44` | 부분 (`price.test.ts:20`) |

- `P`: P0(릴리즈 차단) / P1(주요 기능) / P2(경계·부가). 회귀 확인 케이스도 같은 등급을 매기고
  `검증 항목` 앞에 `[회귀]`를 붙인다. 요약표 집계가 어긋나지 않도록 별도 등급을 만들지 않는다
- `자동화`: 없음 / 부분 / 있음 + 테스트 파일 위치

**경계값은 행을 나눈다.** 한 행에 "0, -500, 0.5, 문자열을 바꿔가며 확인"이라고 적으면
QA는 어차피 4번 실행하면서 어느 것이 실패했는지 따로 기록해야 한다. 값마다 기대 결과가 다르면 행도 나눈다.
P0·P1의 경계값은 특히 그렇다. 반대로 기대 결과가 같은 값들은 한 행에 묶어도 된다.

**회귀 확인 케이스를 반드시 섞는다.** 위 표의 대부분은 "새로 바뀐 것"을 확인하지만,
QA에게는 "안 바뀌어야 하는 것이 그대로인가"도 똑같이 중요하다.
3장 회귀 영향 범위에 올린 기존 기능마다 최소 1건씩, 변경 전과 동일하게 동작하는지 확인하는 TC를 넣는다.

## 7. 자동화 커버리지

| 위험 지점 | 기존 테스트 | 판단 |
|---|---|---|
| R-1 | `tests/price.test.ts:20` | 정상 경로만 검증, 음수 케이스 없음 → 수동 확인 필요 |
```

# 작성 시 판단 기준

**위험 지점(R)과 테스트 케이스(TC)의 관계**: R은 "왜 위험한가"(개발자·리드가 읽는다), TC는 "어떻게 확인하는가"(QA가 실행한다).
하나의 R이 여러 TC로 갈라질 수 있고, 회귀 확인용 TC는 대응하는 R이 없을 수도 있다.

**UI로 도달할 수 없는 경로**: 절차 칸에 실제 검증 수단을 적는다.
예) `1) POST /api/orders 에 items:[] 로 요청 2) 응답 코드 확인` 또는 `유닛 테스트로 calcDiscount(5000, 10000) 직접 호출`.

**사전조건은 재현 가능한 수준까지**: "로그인 상태" 보다 "가입 30일 미만 + 결제 이력 없는 계정".
계정 종류, 데이터 상태, 기능 플래그, 환경(스테이징/운영)을 필요한 만큼 명시한다.

**기대 결과는 관찰 가능해야 한다**: "정상 처리된다"가 아니라 "주문 상태가 PAID로 바뀌고 확인 메일이 발송된다".
코드에서 실제 값(상태값, 에러 코드, 메시지 키)을 읽어와 그대로 쓴다.
