# QA 리포트 작성

코드를 읽고 "여기가 깨질 수 있으니 이렇게 확인하라"를 QA 담당자가 그대로 실행할 수 있는 문서로 만든다.
결과물은 항상 마크다운 파일 1개이며, 테스트 케이스 표를 포함한다.

## 이 문서를 신뢰할 수 있게 만드는 세 가지 원칙

QA 리포트는 사람이 시간을 들여 실제로 수행하는 지시서다. 아래 세 가지가 깨지면 리포트 전체가 버려진다.

1. **모든 항목에 코드 근거를 단다.** 각 위험 지점과 테스트 케이스에는 `경로/파일.ext:123` 형태의 출처를 남긴다.
   근거를 못 붙이겠으면 그 항목은 추측이므로 쓰지 말거나 "확인 필요"로 분리한다.
2. **코드가 실제로 할 수 있는 일만 쓴다.** 존재하지 않는 화면, 버튼, 설정값, 에러 메시지를 지어내지 않는다.
   절차는 코드에서 읽어낸 실제 진입점(엔드포인트, 함수, 이벤트 핸들러, CLI 명령)에서 역산한다.
3. **QA가 재현할 수 없으면 쓸모가 없다.** 사전조건·절차·기대결과를 구체적으로 쓴다.
   UI로 도달할 수 없는 경로라면 그 사실을 적고 API 호출/유닛 테스트 등 대안 검증 방법을 제시한다.

## 진행 순서

### 0. 대상 범위 확정

사용자가 말한 대상을 먼저 확정한다. 불명확하면 기본값은 "현재 브랜치의 변경분"이다.

- 변경분(디프) 기준: PR, 브랜치, 커밋 범위, 작업 트리
- 코드 기준: 특정 파일/디렉터리/모듈 전체

`scripts/collect_context.sh`가 변경 파일 목록, 디프 통계, 관련 테스트 파일 후보를 한 번에 뽑아준다. 먼저 실행해 시간을 아낀다.

```bash
bash <skill>/scripts/collect_context.sh --base origin/main     # 브랜치 변경분
bash <skill>/scripts/collect_context.sh --path src/payment     # 특정 경로
```

변경 규모가 커서 전부 다룰 수 없으면, 임의로 잘라내지 말고 **무엇을 우선 분석하고 무엇을 제외했는지 리포트에 명시**한다.

### 1. 코드 로직 파악

리포트를 쓰기 전에 코드를 실제로 읽는다. 디프만 보면 "무엇이 바뀌었는지"는 알아도 "무엇이 깨지는지"는 모른다.
변경된 함수는 전후 맥락(호출자·호출 대상)까지 열어본다. 최소한 다음을 파악한다.

- **진입점**: 이 코드는 어디서 호출되나 (라우트, 핸들러, 이벤트, 스케줄러, CLI)
- **데이터 흐름**: 입력이 어디서 들어와 어떻게 변형되어 어디에 저장/전달되는가
- **분기**: 조건문, 예외 처리, early return, 기본값
- **상태**: 캐시, 전역/세션 상태, DB, 파일, 외부 시스템
- **경계**: 네트워크, DB, 서드파티 SDK, 파일 I/O 등 실패할 수 있는 지점

### 2. 위험 지점 도출

`references/risk-checklist.md`를 읽고 코드에 대입한다. 카테고리별 질문과 함께 실제로 찾아볼 코드 패턴이 정리되어 있다.
체크리스트를 기계적으로 복사하지 말고, **이 코드에서 실제로 성립하는 위험만** 남긴다.
"입력값 검증 확인" 같은 일반론은 가치가 없고, "쿠폰 금액이 주문 총액보다 클 때 음수 결제금액이 되는지 확인(`order/price.ts:88`)"이 가치 있다.

### 3. 회귀 영향 범위 추적

변경된 공개 함수·타입·API·DB 스키마의 **호출 지점을 실제로 검색**한다(grep/Glob).
QA가 가장 자주 놓치는 것이 "바꾼 곳은 멀쩡한데 쓰던 다른 기능이 깨지는" 경우다.
호출자가 많으면 대표 경로를 골라 회귀 테스트 항목으로 만든다.

### 4. 기존 테스트 커버리지 확인

관련 테스트 파일을 찾아 읽고, 각 위험 지점이 이미 자동화로 덮이는지 판단한다.
이미 단위 테스트가 검증하는 항목은 수동 QA 우선순위를 낮추고, 표의 "자동화" 칸에 표기한다.
자동화가 전혀 없는 위험 지점은 그 자체가 리포트의 중요한 발견이다.

### 5. 우선순위 산정

`영향도 × 발생 가능성`으로 P0/P1/P2를 매긴다. 근거 없이 전부 P0로 만들면 우선순위가 사라진다.

| 등급 | 기준 |
|---|---|
| **P0** | 데이터 손실·유실, 금액/정산 오류, 인증·권한 우회, 전체 기능 불가. 확인 전 릴리즈 불가 |
| **P1** | 주요 기능이 특정 조건에서 오동작, 사용자가 복구 불가능한 상태에 빠짐 |
| **P2** | 드문 경계 조건, 표시 오류, 열화된 상태로도 동작 지속 |

### 6. 리포트 작성

`references/report-template.md`의 구조를 그대로 따른다. 테스트 케이스 표는 필수 섹션이다.

저장 위치는 기본적으로 저장소 루트의 `qa-reports/QA-<YYYYMMDD>-<대상-slug>.md`다.
(저장소에 이미 문서 디렉터리 규칙이 있으면 그 규칙을 따른다.)
작성 후 파일 경로를 사용자에게 알려주고, 대화에는 P0 항목과 전체 건수 정도만 요약한다.

리포트 언어는 사용자·저장소가 쓰는 언어에 맞춘다. 한국어 요청이면 한국어로 쓰되, 식별자·코드 경로는 원문 그대로 둔다.

## 분량 감각

항목 수는 변경 규모에 맞춘다. 30줄짜리 변경에 테스트 케이스 40개를 붙이면 아무도 읽지 않는다.

| 변경 규모 | 테스트 케이스 수 (권장) |
|---|---|
| 파일 1~3개 / 100줄 미만 | 3~8 |
| 중간 규모 기능 | 8~20 |
| 대형 기능·리팩터링 | 20~35 + 범위 분할 명시 |

## 하지 말 것

- 체크리스트 전체를 그대로 붙여넣기 — 해당 코드와 무관한 항목은 노이즈다
- 코드 근거 없는 "일반적으로 ~를 확인하세요" 문장
- 코드를 읽지 않고 디프의 추가/삭제 줄만 보고 쓰기
- 리포트를 쓰면서 코드를 고치기 — 이 스킬의 산출물은 문서다. 명백한 버그를 발견하면 리포트의 "발견된 결함" 섹션에 적고, 수정은 사용자에게 제안만 한다
- 테스트 케이스 절차를 "정상 동작하는지 확인" 수준으로 뭉뚱그리기

## 참고 파일
